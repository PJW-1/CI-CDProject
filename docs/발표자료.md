## 📽️ Slide 2. 3-Tier 분산 마이크로서비스 아키텍처

### 🖥️ [화면 구성]

![아키텍처 데이터 흐름도](images/architecture.png)

* **3-Tier 마이크로서비스 구조:**
  * **Client (스마트폰):** 30fps 비디오 스트림 (Base64 JPEG 480x360, q=0.6 over WSS)
  * **Container A (Gateway :8443):** TLS 자체 인증서 발급 & WSS 라우팅, 1:1 QR 세션 매칭, HTML5 6000x4500 무한 캔버스 렌더링
  * **Container B (Vision :8001):** MediaPipe HandLandmarker (VIDEO 모드), 21개 관절 3D 정규화 좌표 추출 (⭐ 7KB ➔ 500B 좌표로 93% 압축)
  * **Container C (Motion :8002):** 6대 기하학적 제스처 분류, 속도 적응형 EMA 손떨림 필터, 3프레임 디바운스, 비대칭 0초 펜-업

### 🎙️ [대본]
> "시스템 아키텍처를 간략히 설명드리겠습니다. 저희 시스템은 스마트폰 카메라로 손동작을 촬영하여 PC 캔버스를 원격 제어하는 **3-Tier 분산 마이크로서비스**입니다.
> 
> 1. **Container A**는 TLS 보안 게이트웨이로서, QR 코드를 통해 스마트폰과 PC를 1:1 세션으로 매칭하고 비디오 프레임을 중계합니다.
> 2. **Container B**는 유입된 비디오 프레임에서 Google MediaPipe AI를 통해 21개 관절의 3D 정규화 좌표를 추출합니다. 즉, 무거운 7KB 픽셀 이미지를 초경량 500바이트 좌표 배열로 고속 압축하는 역할을 담당합니다.
> 3. **Container C**는 압축된 좌표 간의 기하학적 거리 비율을 분석하여 6대 제스처를 판별하고, 속도 적응형 EMA 필터로 손떨림 노이즈를 제어하여 PC 캔버스에 제어 명령을 전달합니다.
> 
> 이 3-Tier 아키텍처는 기능적으로 완벽히 동작했습니다. **하지만 실제 운영 환경의 관점에서 코드를 진단했을 때, 언제 터질지 모르는 심각한 엔지니어링 결함들이 발견되었습니다.**"

## 📽️ Slide 4. [Pillar 2] 예외 처리와 시스템 복구 탄력성 (Degradation)

### 🖥️ [화면 구성]
* **핵심 기능 3가지:**
  1. **예외 세분화 & 서킷 브레이커:** `TimeoutException`, `ConnectError` 세분화, 30fps 특화 2회 50ms 재시도 + 10회 실패 시 서킷 OPEN
  2. **Graceful Degradation (실측):** 모션 엔진(C) 강제 종료 시 Gateway A 200 생존, 캔버스 보존 & '점검 중' 배너 팝업
  3. **종합 헬스체크 (`/health/ready`):** 하위 B ➔ C 연결성 전이적 검증 (장애 시 503 DEGRADED 보고)

### 🎙️ [대본]
> "두 번째 축은 **'예외 처리와 시스템 복구 탄력성'**입니다.
> 예외처리에 있어서 코드적인 부분에서는 `TimeoutException`(시간), `ConnectError`(연결) 등으로 세분화하여 처리했습니다.
> 
> 보통 웹사이트는 에러가 나면 3초, 5초 동안 계속 재시도를 합니다. 하지만 저희는 스마트폰에서 초당 30장(33ms 주기)의 프레임이 쏟아지는 실시간 시스템입니다. 실패한 옛날 사진 한 장 붙잡고 몇 초씩 재시도하면 뒤에 오는 프레임들이 줄줄이 밀려 극심한 렉(지연)이 발생합니다. 그래서 딱 0.05초(50ms)만 가볍게 2번 다시 찔러보고, 안 되면 옛날 프레임은 버리고 최신 프레임으로 바로 넘어가도록 최적화했습니다. 그리고 연속 10번 실패하면 아예 요청을 잠시 차단하는 서킷 브레이커를 적용했습니다.
> 
> 나아가 **Graceful Degradation(우아한 기능 저하)**을 구현했습니다. 기존에는 모션 엔진이 죽어도 웹서버는 예외를 조용히 삼킨 채 null 좌표를 그대로 PC로 흘려보냈습니다. 튕기지 않으니 오히려 원인을 찾기가 더 어려웠습니다. 하지만 수정 후에는 데이터 스키마(schemas.py)가 기본 좌표를 자동으로 채워주고, 웹서버가 에러를 감지하면 연결을 끊는 대신 상태를 '점검 중'으로 부드럽게 전환합니다.
> 
> 실제로 모션엔진을 끄고 검증에 성공했고 또한 단순히 내 웹서버만 살아있는지 확인하는 게 아니라, 뒤편의 비전과 모션 엔진까지 실제로 정상 작동하는지 한 번에 검진해 주는 종합 헬스체크 엔드포인트(/health/ready)까지 구축하여 복구 탄력성을 높였습니다."

## 📽️ Slide 5. [Pillar 3] 동시성 제어 & 성능 최적화

### 🖥️ [화면 구성]
* **3대 핵심 엔지니어링 해법:**
  1. **스레드풀 오프로딩 (`run_in_threadpool`):** FastAPI 단일 이벤트 루프에서 CPU AI 연산 분리 ➔ 창구 프리징 해소
  2. **`DetectorPool` 세션별 격리:** MediaPipe VIDEO 모드 텐서 세션별 독립 할당 + 단조 증가 타임스탬프 (시간 역전 방지)
  3. **자동 메모리 회수 (LRU + TTL 120초):** 2분 유휴 시 모델 인스턴스 자동 파기
* **동시 4세션 실측 성능 결과:**
  * 처리량: 56.7 fps ➔ **121.6 fps (+114% / 2.1배 폭증)** 🚀
  * p50 지연: 69.1 ms ➔ **24.9 ms (−64% 급감)** ⚡

### 🎙️ [대본]
> "세 번째 축은 **'동시성 제어와 성능 최적화'**이며, 이번 고도화에서 가장 극적인 성능 개선을 달성한 파트입니다.
> 
> 저희 비전 서버는 비동기 프레임워크인 FastAPI로 만들어졌습니다. FastAPI는 수많은 네트워크 요청을 번갈아 처리하는 '단일 이벤트 루프' 방식입니다. 그런데 여기서 용량이 큰 이미지 디코딩과 15~44ms씩 걸리는 무거운 MediaPipe AI 추론을 계산하다보니 프리징이 와 요청을 빠르게 처리하지 못하고 줄줄이 대기열에 갇히는 심각한 병목이 생겼습니다.
> 
> MediaPipe의 비디오 모드는 손동작을 부드럽게 잇기 위해 '직전 프레임의 손 위치'를 메모리에 기억하는 특성이 있습니다. 그런데 단 1개의 AI 모델을 모든 사용자가 공유하다 보니, A의 손 위치와 B의 손 위치가 뒤섞여 손 궤적이 엉망으로 튀는 상태 오염이 일어났습니다. 또한 컴퓨터 시계(time.time())를 쓰다 보니 여러 사람의 요청이 섞여 시간 순서가 뒤집혀 AI 엔진이 튕기는 에러까지 발생했습니다.
> 
> 이런 동시성 제어와 성능 최적화를 3단계 정도로 해결했습니다.
> 
> 1. **스레드풀 오프로딩(run_in_threadpool):** 메인 요청만 받고, 무거운 AI 연산은 뒤편의 여러 워커 스레드에게 던져주어 메인 창구가 0초 만에 다음 요청을 받도록 분리했습니다.
> 2. **DetectorPool 구축:** 세션마다 독립된 전용 AI 모델을 배정하고, 컴퓨터 시계 대신 각 세션마다 '1번, 2번, 3번...' 고유 번호표를 매기는 자체 단조 증가 타임스탬프를 부여해 시간 역전 충돌을 원천 차단했습니다.
> 3. **LRU + TTL 자동 메모리 회수:** 세션마다 AI 모델을 만들면 메모리가 꽉 찰 수 있기 때문에, 사용자가 접속을 종료하거나 2분(120초) 동안 활동이 없으면 가장 오래 안 쓴 모델부터 메모리에서 깔끔하게 청소하여 메모리 누수를 방지했습니다.
> 
> 그 결과, 동일 머신 실측 벤치마크에서 동시 4세션 처리량이 56.7 fps에서 121.6 fps로 114% (2.1배) 급증했고, 지연 시간은 69.1ms에서 24.9ms로 64%나 대폭 단축되었습니다."

## 📽️ Slide 6. [Pillar 4] 구조화 로깅 및 관측 가능성 (Observability)

### 🖥️ [화면 구성]
* **공통 구조화 로거 (`common/logging_setup.py`):** 표준 JSON 스키마, 30fps 스마트 샘플링, 10MB 파일 로테이션
* **`trace_id`를 통한 A ➔ B ➔ C 전 구간 1ms 역추적:**
  ```json
  /* 1. Container A: 스마트폰 프레임 수신 (10:00:00.100) */
  {"ts":100, "container":"A", "trace_id":"user1-frame-45", "event":"frame_received"}
  /* 2. Container B: AI 추론 완료 (10:00:00.115, 15ms 소요) */
  {"ts":115, "container":"B", "trace_id":"user1-frame-45", "event":"inference_done", "detail":{"inference_ms":15.2}}
  /* 3. Container C: DRAW 제스처 판별 (10:00:00.118, 0.5ms) */
  {"ts":118, "container":"C", "trace_id":"user1-frame-45", "event":"gesture_computed", "detail":{"action":"DRAW"}}
  /* 4. Container A: PC 캔버스 전송 완료 (총 20ms 왕복) */
  {"ts":120, "container":"A", "trace_id":"user1-frame-45", "event":"frame_relayed", "detail":{"total_rtt_ms":20.0}}
  ```

### 🎙️ [대본]
> "네 번째 축은 **'구조화 로깅 및 관측 가능성(Observability)'**입니다.

>    * **단위 테스트:** 카메라 없이 21개 관절 좌표를 즉시 만들어내는 **'합성 랜드마크 팩토리'**를 통해, 6대 제스처 판별과 손떨림 보정 공식이 정확한지 검증합니다. 또한 소스 전체를 스캔하여 IP 하드코딩이나 except: pass, print() 같은 안티패턴이 한 줄이라도 있으면 빌드를 강제로 깨뜨립니다.  
>    * **통합 테스트:** 스마트폰과 PC의 1:1 QR 세션 매칭, 방 퇴장 시 메모리 자동 청소, 그리고 엔진이 다운되어도 웹서버가 튕기지 않고 안내 배너를 띄우며 살아남는 **장애 생존성(Degradation)**을 검증합니다.
> 
> 3. **3단계 [비전 격리 테스트 - test-vision (pytest)]:**  
>    pytest의 비전 레이어입니다. 용량이 큰 MediaPipe AI 모델을 깃허브 캐시에서 빠르게 불러와, 2명이 동시 접속했을 때 각자 전용 AI 모델을 받아 **서로의 손 좌표를 간섭하지 않는지(세션 격리)**와 타임스탬프가 꼬이지 않는지를 정밀 검증합니다.
> 
> 4. **4단계 [도커 빌드 및 최종 기동 검사 - build]:**  
>    앞선 테스트들을 모두 통과하면, 실제로 Docker Compose로 3개 이미지를 빌드하고 컨테이너를 가상으로 띄웁니다. 그리고 /health 엔드포인트를 찔러보아 웹서버, 비전 엔진, 모션 엔진 3개가 모두 완벽하게 'Healthy' 상태로 살아나는지 확인한 후 최종 합격(초록불)을 줍니다.
